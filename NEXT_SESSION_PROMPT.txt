== আপডেট: এই zip-এ ৭৯টার মধ্যে সবগুলো (৭৯/৭৯) এরর ফিক্স হয়ে গেছে ==

আগে এই ফাইলে বলা ছিল ২১টা ফিক্স হয়েছে, বাকি ৫৮টা (Admin*View.kt CSV import errors) পরের session-এ করতে হবে।
এখন সেই বাকি ৫৮টাও ফিক্স হয়ে গেছে -- root cause ছিল: এই ১৯টা ফাইলে `com.example.util.CsvImportUtil`,
`com.example.util.CsvParsedResult`, `com.example.util.CsvImportSummary`, আর `kotlinx.coroutines.tasks.await`
-- এই import গুলো ছিল কিন্তু আসলে কোথাও ব্যবহৃতই হতো না (dead/orphaned imports, সম্ভবত পুরনো
Firebase-ভিত্তিক CSV-import ফিচারের অসম্পূর্ণ পরিষ্কার-করা কোড), আর `CsvImportUtil.kt` ফাইলটা প্রজেক্টে
আদৌ ছিলই না। প্রতিটা ফাইলে গিয়ে grep করে নিশ্চিত হওয়া গেছে এই ৪টা import-এর কোনোটাই actual কোডে কোথাও
কল হয় না -- তাই শুধু ওই ৪টা অপ্রয়োজনীয় import লাইন মুছে ফিক্স করা হয়েছে (কোনো ফিচার স্পর্শ হয়নি)।

এখন এই zip দিয়ে বিল্ড করলে compileDebugKotlin-এর সব ৭৯টা এরর আর আসার কথা না। নিচের মূল প্রম্পটটা
(নিচে অক্ষত রাখা হলো) শুধু রেফারেন্সের জন্য রইলো, যদি ভবিষ্যতে নতুন কোনো build error আসে সেক্ষেত্রে
একই পদ্ধতিতে (আগে root cause বের করে, তারপর ফিক্স) কাজ করা যাবে।

## যা আগেই ফিক্স হয়ে গেছে (স্পর্শ করার দরকার নেই, শুধু প্রেক্ষাপটের জন্য জানিয়ে রাখলাম)
- app/src/main/java/com/example/data/remote/SupabaseRealtimeManager.kt — broadcast()-এ JsonObject কনভার্সন যোগ করা হয়েছে
- app/src/main/java/com/example/data/remote/SupabaseSyncManager.kt — FilterOperator import ঠিক করা হয়েছে (postgrest.query.filter প্যাকেজ থেকে), @file:OptIn(ExperimentalTime::class) যোগ করা হয়েছে
- app/src/main/java/com/example/data/repository/SomadhanRepository.kt — releaseEscrow/cloudUser/cloudSolver ডেড-কোড রেফারেন্স ঠিক করা হয়েছে, ৫টা nullable String (?.ifBlank) ফিক্স হয়েছে, @file:OptIn(ExperimentalTime::class) যোগ করা হয়েছে

## প্রথমে যা করবে (root cause বের করা)
1. `CsvImportUtil` ক্লাস/অবজেক্টটা কোথাও প্রজেক্টে সংজ্ঞায়িত আছে কিনা খুঁজে বের করো (`grep -rn "object CsvImportUtil\|class CsvImportUtil"`)। যদি থাকে, প্রতিটা Admin*View.kt ফাইলে সেটার সঠিক import path যোগ করলেই সম্ভবত বেশিরভাগ এরর ঠিক হয়ে যাবে (import missing হওয়াটাই সম্ভাব্য কারণ, যেহেতু এই একই টাইপগুলো একাধিক ফাইলে একই লাইন নম্বরে (~248-271) একইভাবে ব্যর্থ হচ্ছে — এটা copy-paste করা import-block বলে মনে হচ্ছে)।
2. যদি `CsvImportUtil`/`CsvParsedResult`/`CsvImportSummary` আদৌ প্রজেক্টের কোথাও define করা না থাকে (সম্পূর্ণ অনুপস্থিত), তাহলে সেগুলো একটা নতুন util ফাইলে বানাতে হবে — কিন্তু তার আগে প্রতিটা call site (প্রতি ফাইলের ~লাইন ২৪৮-২৭১ এর আশেপাশে) দেখে বুঝে নাও ঠিক কী signature আশা করা হচ্ছে (parse ফাংশনের return type, CsvParsedResult-এর ফিল্ড, CsvImportSummary-এর ফিল্ড, আর 'tasks' রেফারেন্সটা exactly কী প্রপার্টি/ফাংশনের)।
3. প্রতিটা ফাইলে অভিন্ন প্যাটার্ন হওয়ায় একটা ফাইলে root cause বুঝে ফিক্স করার পর বাকি ১৮টাতেও একই ফিক্স apply করা সহজ হবে হবে — কিন্তু প্রতিটাতে গিয়ে আলাদা করে ভেরিফাই করবে (variable নাম বা exact usage সামান্য আলাদা হতে পারে)।

## গুরুত্বপূর্ণ নিয়ম (অবশ্যই মানতে হবে)
- আমার (ইউজারের) app-এর কোনো existing functionality/logic/ফিচার নষ্ট করা যাবে না। শুধু compile error ফিক্স করবে, অন্য কোনো behavior বদলাবে না।
- যেখানে root cause অনিশ্চিত (যেমন dead/leftover Firebase migration কোড কিনা), সেখানে অনুমান করে ফিচার মুছে দেওয়ার আগে পুরো ফাইলের কমেন্ট/কনটেক্সট পড়ে বুঝে নেবে — এই প্রজেক্টে Bengali কমেন্টে migration history লেখা আছে, ওগুলো পড়লে root cause বোঝা সহজ হবে।
- ফিক্স করার পর পুরো প্রজেক্ট zip করে দেওয়ার সময় অবশ্যই নিশ্চিত করবে কোনো ফাইল miss না হয় (zip-এর আগে original file count-এর সাথে মিলিয়ে ভেরিফাই করবে)।
- কাজ শেষে বাকি cutover-related পরিবর্তন (MIGRATION_PROGRESS.md, REALTIME_SCOPING_PROGRESS.md) না ছুঁলেই ভালো, শুধু বিল্ড-ব্রেকিং কোড ফিক্স করো।

মূল error log ফাইলটা (New_Text_Document__2_.txt) এই zip-এর সাথে সংযুক্ত করা আছে যদি আগের পুরো ৭৯-এর তালিকা লাগে।
